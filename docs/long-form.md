# 长篇工具用法

完整命令、分卷 JSON、增量登记、证据、滚动审查与旧作导入示例保存在随作品复制的 [长篇流程](../.agents/skills/writer-project/references/long-form.md)。作者任务入口见 [使用手册](user-guide.md)，具体命令帮助支持 `命令 --help`。

已有作品先运行 `node bin/ai-writer.mjs status --project 目录`，再 `long-enable --expected-revision 当前号`，工具保留旧状态备份。schema 1 仍兼容。schema 2 增加分卷和差量 journal；不要手改 `.writer/state.json` 或删除 journal。

`outline --unit` 与 `context --unit` 自动取当前卷/剧情单元；`recall --query` 用来定位早期线索及正文；`record-template` 返回 changes 格式。`check` 同时校验差量链并报告滚动审查欠覆盖。所有导出仍是草稿。

`rolling_review.stale` 保留所有失效历史记录数；其中 `stale_with_current_coverage` 表示已有一份当前有效报告完整覆盖该旧记录的阅读范围，`stale_without_current_coverage` 表示尚无这样的报告。分段报告不能拼作一次完整连读。旧记录不会重新有效，也不应删除历史来清零；需要补做的每三章滚动窗口看 `pending_windows`。回退后尚未重登的章节也可能落在旧报告范围内。上述数字只表示版本与阅读覆盖，不表示文学质量通过。

分卷范围是全部文体通用的连续单元号；小说一般按章，剧本可按场/集，历史散文按章。物证/人物知识账本按任务需要使用，不强迫散文采用小说结构。历史事实仍必须经过原来的 research_refs 事实卡流程，ledger 不替代史料核验。

当前卷纲哈希按整文件保护，已消费卷纲的任何修改都需核实影响后回退；未来章纲可滚动细化，尚无卷内未来arc免回退的细粒度修订。旧稿输入只支持明确排序的UTF-8分章文件，合订本先保留原文并拆章。修订报告建议另存带修订号的新文件，保留原报告，旧覆盖不会自动升级为新稿结论。

Windows 本机既有实跑中，Codex CLI 以嵌套作品目录为 cwd 时曾遇到 helper 启动失败；从 ai-writer 根目录启动并显式传作品路径后完成恢复续写。遇到同类错误时使用根目录入口，不修改全局安全设置。独立作品的 Node 轻量工具可用于诊断；具体历史证据保存在主项目 acceptance/20261015-long/。

旧稿移动后看 import-status 的 can_continue/blockers，用 [import-relink](workflow.md) 绑定同一冻结内容的新位置。正文目录内的未登记稿由 status/check 主动列出；导出时核对 excluded_drafts。

## 新会话怎样接住旧章修改

先检查当前状态、正文与来源漂移，再读取当前卷纲、章纲、相关人物和原文。跨卷回收至少回读线索首次出现、最近变化及本次兑现处；恢复说明应列出人物分别亲见、看照、听述了什么，原物由谁保管，哪些仍只是约定。不要从旧聊天或修前报告补回已被改掉的情节。

修改多处旧章时，先保存修前正文、状态和登记输入，找最早受影响的已消费来源，再正式回退重登。最早正文变化和最早来源消费者可能不同：全局规则在第1章已消费，即使物件第3章才出现，也不能只从第3章处理。比较回退前后全部稳定ID、观察事实、到期值、证据与知识，未改原句的证据应保留并绑定当前正文；不靠推迟到期或删除未知项清零。

## recall 的查询范围

`recall --query` 在账本ID及内容、章节号及摘要中做不区分大小写的关键词定位，不搜索完整正文，也不进行语义理解。空白分隔的词必须**全部匹配（AND）**，并非多个ID任选其一；把 `T_SIGNAL T_TAPE` 拼成一次查询可能没有结果。

```powershell
node bin/ai-writer.mjs recall --project works/雨夜来信 --query T_SIGNAL --limit 20
node bin/ai-writer.mjs recall --project works/雨夜来信 --query T_TAPE --limit 20
```

多ID按项查询，或在章纲的 `recall_ids` 数组中显式召回。`--limit` 是返回条目数，最多100；`--max-chars` 属于 `context` 的字符预算，不能用于 `recall`。召回结果和 `omitted_ids` 都只是定位线索，相关正文仍须实读。

## 回收后还要检查人物是否真的知道

同一事件可能分布在主线、物件、观察、读者总览及人物快照中。仅更新 `status`、`custody` 或 `reader_known`，仍可能让 `character_known` 停在“明早待签收”“尚未听过”。实际完成交接、补录或查访后，逐项核对关联条目的当前知识，而不只检查主线是否 resolved。

把当前知识与“截至第几章”的历史分开；保留仍有效的内容，不把过时的未来计划留在当前结论中。罗敬未参加第4章原带短听，与第23章已听完整工作转录可以同时成立。陪运后离场、看照片、听电话都不等于亲见签收；作者知道最终保管人，也不能自动同步给所有角色。知识更新应有实际正文和版本绑定引文支持。

保留历史不等于无限复制整段旧摘要。可以精炼当前知识，但要逐项比较仍有效的信息和证据，历史原记录由journal与修前备份保留。`check`、引文哈希以及滚动审查覆盖只做机械核验，不能发现全部语义陈旧，也不保证旧报告中的账本结论适用于新的追踪状态。

`review`绑定的报告保存在作品的`审查/`目录；阶段日志、核验脚本和导出可另存指定目录。报告应区分实际阅读、机械检查和未证明事项。完整实例见 主项目的 `acceptance/20261016-expanded/README.md`（验收目录不随独立作品复制），其中r63机械通过后仍发现知情陈旧，经正式修订到r67才完成本轮复核。
